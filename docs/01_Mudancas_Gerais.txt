COMO INTERPRETAR
- IDs dos requisitos preservam a numeração da fonte. Txxx/Rxxx identifica tabela/linha,
  contando a partir de zero na ordem do documento, para rastreabilidade sem paginação variável.
- "Sim" indica solicitação de implementação na fonte, não comprova implementação.
- Campo "Implementar?" vazio significa decisão pendente. Requisito dependente de outro
  item marcado Sim é identificado, mas a inconsistência da marcação é preservada.
- Detalhamento da fonte é reproduzido em cada requisito para conservar campos, exemplos,
  condições, exceções e fluxos. Exemplos não constituem listas fechadas de domínio.
- Critérios de aceite e regras consolidadas são operacionalizações propostas para revisão.
  Decisões ausentes não foram convertidas em regras definitivas.
- Referências a capturas de concorrentes são referências visuais do DOC original; imagens
  não são reproduzidas em TXT. Não foram inferidas regras a partir de elementos só visuais.
- Não há definição de banco físico, linguagem, endpoints ou cronograma nesta versão.


01 — Mudanças Gerais: a Serem Aplicadas em Todos os Módulos do Green

OBJETIVO
Especificar as mudanças deste tema preservando o escopo e as ressalvas da Revisão G.

ESCOPO CONSOLIDADO
Aplicar aos módulos Legal, Licenças, Medição e Monitoramento, Controle/GED,
Treinamento, Infraestrutura, Homologação, RNC, Auditoria e ESG quando houver escopo definido.
Home: logos do Green e cliente, identificação/foto do usuário, cards, gráficos/tabelas,
pendências, próximas tarefas e navegação por clique para o conjunto filtrado.
Painel gerencial: consolidar módulos contratados, unidades e responsáveis, permitindo
acompanhar tarefas feitas, não feitas e futuras; formato como módulo separado é sugestão.

PENDÊNCIAS ESPECÍFICAS
- Definir fórmulas dos indicadores e limiares de proximidade do vencimento.
- Definir quando configurações pessoais de email exigem permissão administrativa.
- Definir alcance e precedência da delegação, datas de vigência e pendências existentes.
- Definir origem e periodicidade da verificação de usuários ativos.
- Resolver logs contratáveis versus históricos obrigatórios dos itens 18.1–18.3, 36 e 41.
- Definir retenção, volume, exportação, destinatários e frequência de envio de logs.
- Itens 6, 10 e 12 não possuem marcação Sim: filtros favoritos, token API e Power BI.
- Token API não substitui logs nem prova, por si só, vínculo ativo do usuário à empresa.
- Definir eventos, periodicidades, repetição e encerramento das pendências e notificações.
- Definir quais transições do fluxo são obrigatórias e quais são facultativas.

GER-10 — Implementar token API

Origem: item 10; T007/R000
Situação: DECISÃO PENDENTE (Implementar? não preenchido)

COMPORTAMENTO / DADOS / REGRAS — DETALHAMENTO DA FONTE
O sistema do concorrente possui um negócio chamado Token API veja imagem abaixo.

Pelo que entendi, o token API é um token de acesso, ou seja, uma chave ou código criptográfico exclusivo gerado por um sistema de software para conceder a aplicativos, sistemas ou usuários o acesso autorizado a uma API, ou seja, um passaporte digital ou um crachá de identificação. Em vez de enviar o login e senha normais, a pessoa envia esses tokens nas suas requisições para provar que tem permissão para ler, alterar ou deletar dados naquele sistema. Não sei se isso é algo funcional para nós. Pelo que verifiquei, as principais características do token de API incluem:
Autenticação e Segurança: valida quem está fazendo a solicitação, permitindo ou negando o acesso.
Controle de Permissões: estabelece limitações específicas. Por exemplo, permitir apenas a leitura de dados (GET) e não a exclusão (DELETE).
Validade: são configurados para expirar após um determinado período de tempo, o que diminui o risco caso o código seja vazado.

Não sei se isso faria sentido implementar um negócio desses para:
Garantir a segurança dos dados do sistema (evitar, por exemplo, ter que gerar os logs)
Fazer a integração com outros softwares
Garantir que apenas usuários ativos acesse o sistema

Esse fluxo é bem interessante de ser aplicado em todos os módulos. As atividades de GESTÃO de todos os módulos, de alguma forma, funcionam como um processo. Seguem os workflows dos módulos:

. No módulo legal a pessoa:
1- recebe a lei
2- valida a lei (decide se ela vai ser mantida no banco ou retirada do banco)
